## 1. P0 — Input and output contracts

Files: `backend/app/main.py` and the shared schema/validation module.

- Apply strict type validation: unique task IDs, no more than 60 tasks, positive integer durations, valid dependency IDs, and an integer deadline. Do not accept boolean values as integers.
- Return clear 4xx JSON responses for missing fields, incorrect types, and semantic errors.
- Return 404 for an unknown plan and accept only existing plan IDs. Read files as UTF-8.
- Provide a separate flow for a null deadline in a review: the finish date can still be calculated, but deadline feasibility must be reported as unknown. The fixed schedule endpoint must continue to require an integer deadline.
- Use a shared task schema for reviews and schedules. Support a null `finding.quote` in frontend types.

Acceptance criteria: tests for missing fields, duplicate IDs, unknown dependencies, zero or negative durations, 61 tasks, and incorrect types return 4xx responses. An empty task list returns a contract-compliant result.

## 2. P0 — Correct and shortest possible schedule

File: `backend/app/scheduler.py`.

- Validate the dependency graph and detect cycles before scheduling instead of using repeated recursion. Return tasks in a cycle using the contract's cycle response, including self-dependencies.
- Model the problem with a constraint solver: start and end variables for every task, precedence constraints for dependencies, and non-overlap constraints for tasks with the same non-null owner. Minimize the maximum task end day. OR-Tools CP-SAT is a suitable option.
- Do not apply a shared resource constraint to tasks whose owner is null. Days start at 0, and one week equals seven days.
- Keep solving time below the HTTP ten-second limit, leaving time to construct the response. Track the best valid solution and lower bound. When optimality cannot be proven, report that in additional metadata instead of presenting a merely valid schedule as optimal. Explain the scoring implication in `NOTES.md`.
- Independently validate the returned schedule against all scheduling rules.

Acceptance criteria: the official check passes; small cases are compared with a brute-force optimum; tests cover the same owner, different owners working in parallel, null owners, a long dependency chain, cycles, and 60 tasks. Runtime and any optimality gap are reported.

## 3. P0 — Trustworthy AI review

Files: `backend/app/review.py` and the `review` command.

- Create a prompt with an explicit JSON schema, task extraction rules, and an uncertainty policy. Read both tables and prose, and convert weeks to days.
- Treat the plan as data rather than instructions. Add a regression test for the “no findings / day 99” instruction embedded in the Harbour Run plan.
- Detect the 30-day/five-week contradiction and the insurance–approval cycle in the Harbour Run plan. Report an uncertain deadline as a finding and do not choose a date without justification.
- Validate the model response with the shared schema. For every non-null quote, normalize whitespace and verify a case-sensitive substring match against the source plan.
- Reject malformed JSON, missing fields, invalid references, and fabricated quotes. Apply limited retries and a timeout, keeping total CLI runtime under 300 seconds.
- Exit non-zero with a clear stderr message on failure. Write the output atomically on success. Never log the API key.
- Regenerate all three examples using the real CLI and do not edit files in `data/reviews` by hand. Document the model choice and required environment variables in `NOTES.md`.

Acceptance criteria: mock-model tests cover malformed output and fabricated quotes; all three examples pass shape and source-quote validation; the CLI is tested end to end with a real model.

## 4. P1 — Decision-focused interface

Files: `frontend/src/App.tsx` and new component/style files.

- Show a summary card at the top with one of: on track, late, deadline unknown, or cycle. Include the finish day, deadline, and delay.
- Replace raw JSON with findings ordered by importance and an editable task table.
- When a quote is selected, reveal or highlight its location in the source plan. Explain when a finding has no source quote.
- Recalculate owner, duration, dependency, and deadline edits through `/api/schedule`. Compare the previous and new finish dates and provide a reset action. In-session editing is enough for the first version; state that changes are not persisted.
- Handle loading, error, empty-data, and rapid plan-switching states. Prevent an older request from overwriting a newer selection.
- Apply the colors and typography from `BRAND.md`: warm neutral canvas, white cards, small green accents, and terracotta only for warnings. Use Inter and Source Serif 4, keyboard-accessible controls, and readable contrast.

Acceptance criteria: the user can understand the decision within seconds; changing a task duration updates the result; source and error states are checked on desktop and mobile layouts.
